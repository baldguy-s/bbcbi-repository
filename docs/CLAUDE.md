# docs/ — bible-institute-notes, GitHub Pages edition

This is the only version of this app — served as static HTML/JS by GitHub Pages, no server at all. It reads/writes the notebook by committing directly to this repo (`baldguy-s/bbcbi-repository`) via the GitHub REST API, gated by a Personal Access Token pasted into the page and stored in `localStorage`. Same pattern as the sibling `choir-vault` and `bbcff-serv-sched` repos.

An earlier Express + SQLite version (meant to run locally) existed at `bible-institute-notes/` in this repo and was deliberately deleted once this GitHub Pages version was working — the user wanted one app they could reach from a URL, not two to keep in sync. `notebook.js`, `session.js`, `inbox.js`, `upcoming.js`, `scripture.js`, `search.js`, `upload.js`, `util.js`, and `scriptureParser.js` started as copies of that version's frontend (it only ever talked to a small `api.js` module — `api.get/post/put/patch/del` — so swapping that module's implementation, real HTTP → in-memory tree persisted to GitHub, required no changes to the view code). `api.js` here reimplements what were once Express routes as plain JS over an in-memory array-of-objects tree (`DB.years`, `DB.semesters`, ...), loaded once from `data/notebook.json` and saved back as a whole file on every mutation. `github.js` is the only thing that actually talks to GitHub.

## Traps already hit once — don't reintroduce these

**Scope every delegated click listener to its own level, explicitly.** `session.js` had two delegated `click` listeners on nested containers: one on `#sessions-list` for session-level actions (up/down/edit/delete), one per `.entry-card` for entry-level actions. Both used `ev.target.closest('[data-action]')`. Because entry-cards are nested inside session-cards, clicking an entry's Edit button bubbled up and matched the SAME `[data-action="edit"]` element in the outer listener too — so editing one note also popped a `prompt()` to rename the whole session, and deleting one note also asked to delete the whole session. Fixed by scoping the outer listener's lookup to `ev.target.closest('.session-card-header [data-action]')` instead of the bare `'[data-action]'`. **Any time you add a new delegated listener on a container that has another delegated listener (or a per-element listener) somewhere inside it, scope the `closest()` selector to the specific wrapper that action belongs to — never just `[data-action]` alone.** A `prompt()`/`confirm()` triggered this way blocks the entire page's JS thread indefinitely under headless/automated testing (no dialog handler = hang forever), which is how this was originally found — a hang with no error, not a crash.

**Render-staleness guard (`app.js`: `bumpRenderToken()` / `currentRenderToken()`).** Every `route()` call and the debounced search handler bump a token; each fetch-then-render view function (in `notebook.js`, `session.js`, `inbox.js`, `upcoming.js`, `scripture.js`) captures the token before its fetch and re-checks it right before writing to the DOM, bailing out if a newer navigation started meanwhile. Add this same two-line guard (`const myToken = currentRenderToken(); ...await...; if (myToken !== currentRenderToken()) return;`) to any new view function that fetches then writes to `innerHTML` — otherwise a slow response to an old navigation can land after a fast response to a newer one and silently clobber it.

**`navigate()` is a no-op when the hash isn't actually changing** (`app.js`), including the `'' == '#/notebook'` special case (both render the same default view but are different hash strings). Without this, clicking a nav button while already on that view fires a real, wasted `hashchange` → re-fetch → re-render, which can race with whatever the user (or a fast test) is doing on the still-current page. If you add more "same view, different entry hash" cases, extend this check.

**Only one element may be `position: sticky; top: 0` in a given stacking context.** `header.site` (the banner) and `.sticky-bar` were both `top: 0` at one point; once scrolled past the banner's natural height, the sticky bar crept up and overlapped/collided with the banner instead of stacking below it. Fixed by making only `.sticky-bar` sticky — the banner scrolls away normally. If the banner needs to be sticky again, give `.sticky-bar` a `top` offset equal to the banner's actual rendered height, not `0`.

**Sessions auto-expand when created** (`expandedIds.add(String(created.id))` in `session.js`, right after creation). This is deliberate UX (a newly added session's entry form should be immediately usable), but it means "add a session" and "session card is expanded" are the same event, not two — don't write test/automation steps that click the header to "open" a just-created session, that would *collapse* it instead.

**`class_docs` rows are eagerly created on read**, not lazily on first save (`api.js`'s `GET /api/classes/:id/docs/:docType` handler). The frontend's upload widget for a syllabus/schedule doc needs a real `class_doc_id` the moment the tab renders, before the user has typed or saved anything — lazy creation left it `undefined` until the first manual save, breaking uploads to an unsaved doc.

**No sibling backend precedent exists anywhere in the workspace.** `choir-vault` and `bbcff-serv-sched` are both static GitHub Pages sites — this app's GitHub-API-as-backend approach is the same *pattern* as those, but was still assembled from scratch for this app's specific data shape. The *visual* tokens/patterns (CSS vars, dark-mode-on-`<html>`, chip filters, collapsible cards, localStorage key conventions, the `header.site` banner + logo treatment) were reused exactly from `bbcff-serv-sched/schedule-display.html` and `choir-vault` — those files are the real source of truth for brand/UI conventions, worth re-checking directly rather than trusting a paraphrase of them (including this one).

## Traps hit getting the GitHub-API layer reliable — all three needed together

Getting reliable read-after-write consistency out of the GitHub API took three separate fixes; each alone looked like it should be sufficient but wasn't:

1. **Path prefixing.** `github.js` talks to the GitHub API in repo-root-relative paths, but the site is served from `docs/`, so `api.js` (and the site itself, via relative `fetch()`) work in *site*-relative paths (`data/notebook.json`, `uploads/session-3/x.jpg`). Every path has to be translated through one place (`repoPath()` in `github.js`) before it reaches a GitHub API call. Getting this wrong doesn't 404 loudly — it silently reads/writes a *different, wrong-path file* that happens to also be creatable at the wrong location (a bare `data/notebook.json` at the repo root, invisible to the deployed site, quietly accumulated an entire test run's worth of data before this was caught).

2. **Don't use the Contents API's convenience read/write for anything read back soon after writing.** `GET/PUT contents/{path}` is simple but sits behind a layer that observably lags the true git state for a few seconds under back-to-back edits or a reload shortly after a write — a delete right after a create could be silently lost, and a reload right after a create could show the pre-create state. Both writes and reads now go through the raw Git Data API instead: blobs → trees (`git/trees/{sha}?recursive=1` to read the whole tree in one call rather than walking it level by level) → commits → moving the branch ref. Every commit's parent is **our own last-known commit sha**, tracked in a module-level variable (`chain` in `github.js`) and updated after each write — not re-fetched from `git/ref/heads/main` before each write — so a rapid sequence of edits chains correctly without racing to read GitHub's own state.

3. **`cache: 'no-store'` on every `fetch()`.** `github.js`'s `ghFetch()` didn't set it and needs to — `git/ref/heads/main` in particular is the *same URL* on every single read, and without `cache: 'no-store'` the browser's own HTTP cache can serve a stale response to it, independent of anything happening on GitHub's side. This one only reproduces in an actual browser (`fetch` in a plain Node script doesn't have this cache), which is why it survived a fully-passing Node-level test suite and only showed up on a real page reload. If this app ever makes any other `fetch()` call (to anything, not just GitHub) that gets re-read shortly after a write, set `cache: 'no-store'` on it too, on the first pass — this bug class has already recurred once from knowing about it in the abstract but not applying it everywhere.

If something still looks like a stale-data bug after this, suspect a *fourth* layer before re-litigating any of the three above — these were each confirmed independently (Node-level tests isolate #1 and #2 from browser caching; the real-browser reload test isolates #3).

## Testing this

- **The data/API layer can be tested directly in Node** (no browser) — `fetch`, `btoa`/`atob`, `TextEncoder`, and `crypto.randomUUID` are all native in Node 18+, so `github.js`/`api.js` can be dynamically `import()`-ed from a plain `.mjs` script with a trivial `Map`-backed `localStorage` polyfill. Use `gh auth token` to get a real token with `repo` scope for this — no need to create a separate PAT. This is far faster and more reliable than driving a browser for anything that doesn't need the DOM, and it's what caught bugs #1 and #2 above.
- **Every test run against the live repo creates real commits.** Clean up whatever you create (the test scripts here delete their own test years, which cascades) — don't leave `TEST-`/`BROWSERTEST-`-prefixed junk in `data/notebook.json`. If you do leave debris, `gh api repos/baldguy-s/bbcbi-repository/contents/docs/data/notebook.json --jq '.content' | base64 -d` shows the live state (or walk `git/trees` directly if you suspect the Contents API is lying to you — see trap #2).
- **Real create/reorder/delete actions take noticeably longer than on the Express app** — each one is 3-4 sequential GitHub API calls (blob create, tree create, commit create, ref update), not one local DB write. Give the UI a few seconds, not a few hundred milliseconds, before deciding an action didn't work. `showApp()` shows a "Loading notebook from GitHub…" message for exactly this reason on the initial load, which is the slowest single operation (ref + commit + recursive tree + blob).
- GitHub Pages itself takes roughly 30-90 seconds to rebuild after a push before changes are live at `https://baldguy-s.github.io/bbcbi-repository/` — poll `gh api repos/baldguy-s/bbcbi-repository/pages/builds/latest --jq '.status'` for `"built"` rather than guessing a sleep duration.
