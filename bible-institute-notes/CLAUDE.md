# bible-institute-notes — notes for future work

Local Express + better-sqlite3 backend, vanilla ES-module frontend (`public/js/*.js`, loaded via `<script type="module">`, real `import`/`export` — no bundler). Full spec is `../bible-institute-notes-BUILD_BRIEF.md`. This file is the durable, codebase-specific record of traps hit while building it — read it before touching event delegation, caching, or the sticky header.

**A second, no-backend version of this app lives in `../docs/`** (GitHub Pages, reads/writes this repo directly via the GitHub API instead of a server) — its frontend is a copy of this one's. See `../docs/CLAUDE.md` for that version's own traps, several of which are the same bug class as below (caching, event-delegation) rediscovered independently.

## Traps already hit once — don't reintroduce these

**Scope every delegated click listener to its own level, explicitly.** `session.js` had two delegated `click` listeners on nested containers: one on `#sessions-list` for session-level actions (up/down/edit/delete), one per `.entry-card` for entry-level actions. Both used `ev.target.closest('[data-action]')`. Because entry-cards are nested inside session-cards, clicking an entry's Edit button bubbled up and matched the SAME `[data-action="edit"]` element in the outer listener too — so editing one note also popped a `prompt()` to rename the whole session, and deleting one note also asked to delete the whole session. Fixed by scoping the outer listener's lookup to `ev.target.closest('.session-card-header [data-action]')` instead of the bare `'[data-action]'`. **Any time you add a new delegated listener on a container that has another delegated listener (or a per-element listener) somewhere inside it, scope the `closest()` selector to the specific wrapper that action belongs to — never just `[data-action]` alone.** A `prompt()`/`confirm()` triggered this way blocks the entire page's JS thread indefinitely under headless/automated testing (no dialog handler = hang forever), which is how this was originally found — a hang with no error, not a crash.

**All API `fetch()` calls use `cache: 'no-store'` (see `public/js/api.js`).** Without it, the browser's HTTP cache can serve a stale `GET` response to a legitimate, non-duplicate request (observed: a `GET /api/years` returned `304` with pre-mutation data moments after a `POST` had already succeeded, because two navigations fired close together and the browser cache decided the second GET was "unchanged"). This wasn't a bug in app logic — the JS did everything right; the browser just lied about what the server currently has. Keep `cache: 'no-store'` on every apic all.

**Render-staleness guard (`app.js`: `bumpRenderToken()` / `currentRenderToken()`).** Every `route()` call and the debounced search handler bump a token; each fetch-then-render view function (in `notebook.js`, `session.js`, `inbox.js`, `upcoming.js`, `scripture.js`) captures the token before its fetch and re-checks it right before writing to the DOM, bailing out if a newer navigation started meanwhile. Add this same two-line guard (`const myToken = currentRenderToken(); ...await...; if (myToken !== currentRenderToken()) return;`) to any new view function that fetches then writes to `innerHTML` — otherwise a slow response to an old navigation can land after a fast response to a newer one and silently clobber it.

**`navigate()` is a no-op when the hash isn't actually changing** (`app.js`), including the `'' == '#/notebook'` special case (both render the same default view but are different hash strings). Without this, clicking a nav button while already on that view fires a real, wasted `hashchange` → re-fetch → re-render, which can race with whatever the user (or a fast test) is doing on the still-current page. If you add more "same view, different entry hash" cases, extend this check.

**Only one element may be `position: sticky; top: 0` in a given stacking context.** `header.banner` and `.sticky-bar` were both `top: 0` at one point; once scrolled past the banner's natural height, the sticky bar crept up and overlapped/collided with the banner instead of stacking below it. Fixed by making only `.sticky-bar` sticky (the banner scrolls away normally — the brief only requires the *control bar* to stay sticky). If the banner needs to be sticky again, give `.sticky-bar` a `top` offset equal to the banner's actual rendered height, not `0`.

**Sessions auto-expand when created** (`expandedIds.add(String(created.id))` in `session.js`, right after `POST`). This is deliberate UX (a newly added session's entry form should be immediately usable), but it means "add a session" and "session card is expanded" are the same event, not two — don't write test/automation steps that click the header to "open" a just-created session, that would *collapse* it instead.

**`class_docs` rows are eagerly created on `GET`**, not lazily on first `PUT` (`routes/classes.js`). The frontend's upload widget for a syllabus/schedule doc needs a real `class_doc_id` the moment the tab renders, before the user has typed or saved anything — lazy creation left it `undefined` until the first manual save, breaking uploads to an unsaved doc.

**No sibling backend precedent exists anywhere in the workspace.** `choir-vault` and `bbcff-serv-sched` are both static GitHub Pages sites with zero server code — no Express, no SQLite, no session auth, no multer, despite the build brief's assumption that a "kanban-app" pattern existed to copy. The auth/session/upload layer here was designed from scratch (bcryptjs, express-session MemoryStore, multer diskStorage). The *visual* tokens/patterns (CSS vars, dark-mode-on-`<html>`, chip filters, collapsible cards, localStorage key conventions) were genuinely reused from `bbcff-serv-sched/schedule-display.html` — that file is the real source of truth for brand/UI conventions, not the build brief's paraphrase of it.

## Testing notes for this environment

No Chrome extension is connected here (`mcp__claude-in-chrome__*` tools fail with "extension not connected"), so UI verification has to go through a locally-launched Puppeteer against the system Chrome (`C:\Program Files\Google\Chrome\Application\chrome.exe`, via `puppeteer-core` installed in a scratch dir — not a project dependency). Two things cost a lot of time before they were understood:

1. **Reset `db/notebook.sqlite` and `uploads/` before every test run.** Leftover rows from a previous run mean a selector like `.row-item .row-label` (which always matches the *first* match) clicks stale data instead of what the current run just created, producing confusing failures that look like app bugs.
2. **Puppeteer's native `page.click()` was unreliable in this sandbox** for reasons ranging from web-font-load layout shift to plain CDP timing flakiness — confirmed repeatedly via direct `getBoundingClientRect()` checks showing the target was valid, visible, and stable when `page.click()` still threw or hung. `page.evaluate(() => el.click())` (a real DOM click, same handlers, no Puppeteer geometry/hit-testing) was reliable every time it was tried and is what surfaced the real event-delegation bug above (native `page.click()` was hanging on the entry Edit button for reasons that turned out to be the `prompt()` dialog, not a Puppeteer issue — but getting to that diagnosis took a lot of chasing red herrings before switching click methods). Prefer JS-native clicks for automation here.
